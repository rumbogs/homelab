# 04: ADR-0001 in your own words

- Plan phase: 1 (repo skeleton)
- Tags: ARCH, K8S

## Goal

Write ADR-0001, "Kubernetes on a single node", yourself. It answers the
question every interviewer will ask about this project: why Kubernetes
for one machine? The Decision section must fit in 30 seconds out loud.

## Context

- Today the server runs Proxmox with several LXCs, some running Docker
  with docker-compose inside. Each one is set up by hand. Docker-in-LXC
  needs workarounds: AppArmor unconfined, nesting, and bridge NAT that
  an `apt upgrade` has broken before.
- The plan: one VM on Proxmox running k3s, managed by Flux from this
  repo. One replica of each service, one machine. A second worker VM may
  come later, to learn scheduling, taints and drains.
- The harness (an AI agent that diagnoses outages) will run in the
  cluster with a ServiceAccount and a read-only Role.
- Already decided: k3s, not Talos (Talos may be a later experiment).
  The ADR argues the decision; it doesn't reopen it.
- ADR format: `docs/adr/0000-template.md`. Sections: Context, Decision,
  Alternatives considered (a table), Consequences.
- `main` is protected: the ADR lands through a PR with green `secrets`
  and `harness` checks.

## Concepts

- An ADR records one decision: the context that forced it, what was
  chosen, what was rejected and why, and what it costs. It's written
  once and superseded by a new ADR, not edited, when the decision
  changes.
- Reconciliation: you declare desired state (a Deployment with one
  replica); a controller compares it with actual state in a loop and
  acts on the difference (the ReplicaSet controller recreates a missing
  pod; the kubelet restarts a crashed or liveness-failing container).
  Compare with docker-compose `restart: always`, which restarts a
  container when it exits; it ignores a failing healthcheck and doesn't
  fix drift in config, volumes or networking.
- Declarative vs imperative: `kubectl apply` of a file vs a sequence of
  `docker run` and `pct set` commands someone has to remember.
- One API: Deployments, ConfigMaps, Secrets, Services, PersistentVolumes
  and RBAC are all objects with the same shape, stored in the same
  place, applied the same way.
- GitOps: the repo is the source of truth and a controller in the
  cluster (Flux) pulls it. Rebuilding the server means "install k3s,
  point Flux at the repo, restore data" (plus any keys that can't live
  in git, such as the one that decrypts secrets).
- Workload identity: the kubelet mounts a projected ServiceAccount
  token that the cluster issues, bound to the pod (invalid once it's
  deleted), expiring (default 1h) and rotated automatically. A
  RoleBinding grants the ServiceAccount a Role's permissions. An API
  token in a file is usually long-lived, rotated by hand, and often as
  powerful as whoever created it.
- k3s: a CNCF-conformant Kubernetes in one binary. A single server
  uses SQLite instead of etcd by default (embedded etcd is for HA) and
  bundles extras: containerd, Flannel, CoreDNS, Traefik, ServiceLB,
  local-path storage, metrics-server.
- Honest costs: about 1–1.5GB RAM for the control plane, many more
  moving parts, and no HA. One node failing takes everything down, same
  as today.
- Good ADR alternatives are real options someone would pick, with the
  reason that applies here, not a generic weakness.

## Questions to answer

- "Why not docker-compose on one VM? It's simpler." Answer in two
  sentences.
- What does a controller do that `restart: always` doesn't?
- If the node dies, what is lost and what comes back by itself?
- Rebuilding from the repo: what isn't in git, and where does it live?
- What would make you supersede this ADR?
- Why does a ServiceAccount beat a token in a file for the agent?
